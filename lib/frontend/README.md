# Frontend — Vanilla Vite + Svelte 5 SPA

Single-page UI for exploring AI-LinkMO data via the FastAPI backend.

This is a plain Vite SPA that uses Svelte 5 (runes), `svelte-routing` for client-side routes, and `index.html` as its entry.

## Quick Start

```bash
npm install
npm run dev      # http://localhost:5173, with /classes, /risk, /action, ... proxied to :8000
npm run check    # svelte-check (TS + Svelte)
npm run lint     # prettier --check + eslint
npm run test     # vitest (unit and browser projects)
npm run build    # production build to dist/
npm run preview  # serve dist/
```

The dev server proxies API endpoint paths (`/classes`, `/risk`, `/action`,
`/health`, …) to `http://localhost:8000`. Keep `API_ENDPOINTS` in
[`vite.config.ts`](vite.config.ts) in sync with the endpoints in
[`src/lib/entities.json`](src/lib/entities.json) and the FastAPI routes.

## Generated entity list

`src/lib/entities.json` is written by `just gen-ui-config` (from the project root)
out of `lib/api/api.yaml`, the file that says which ontology classes the API
exposes. Each entry carries the endpoint key, which is also the API route, the
class name, the bring-your-own-data section, and default filter and prominent
field lists derived from the schema. Do not edit it by hand: rerun the recipe
when `api.yaml` or the installed `ai-atlas-nexus` changes, and
`lib/test/test_ui_config.py` fails while it is behind. The hand-written part is
the overlay in [`src/lib/constants.ts`](src/lib/constants.ts): the accordion
groups, label overrides, and the filters shown per endpoint.

## Key files

### `src/lib/constants.ts`

Main configuration file. Customize application behaviour here:

- Application metadata (name, logos, URLs)
- API endpoints, UI accordion groups, and backend integration
- UI dimensions and layout parameters
- UI wanted filters per endpoint (field names from `filters.svelte.ts`)
- UI personas (demo users)

### `src/lib/components/ui/Record/RecordForm.svelte`

The add and edit form is generated by
[@sjsf](https://x0k.dev/svelte-jsonschema-form/) from the JSON Schema in
`static/schema/`, drawn with its daisyUI 5 theme, and checked with ajv before
the record is saved. [`src/lib/utils/recordForm.ts`](src/lib/utils/recordForm.ts)
prepares the endpoint's class for it: the class definition is copied with the
definitions its slots refer to under `$defs`, so @sjsf and ajv resolve each
`$ref` against it, and slots ranging over `Any` become strings because the
records hold identifiers there. Slots that point at other records suggest
their identifiers as you type.

Some of the form stays in the app's hands, as it did in the hand-built form.
The taxonomy file a record is saved to is chosen above the generated fields.
The dates and the taxonomy slot are filled in by the app and not shown. The
class designator is read-only, so a record of a subclass keeps its own type.
[`src/lib/app.css`](src/lib/app.css) loads daisyUI 5 for the components the
theme uses: fieldset, input, select, textarea, button and join.

### `src/lib/states/filters.svelte.ts`

Reactive filter state management using Svelte 5 runes:

- Maintains search and filter parameters
- Generates dropdown options
- Owns filter validation and application logic
- Extend functionality by adding new filter fields here
- Aligned to the classes `lib/api/api.yaml` exposes; the filter names are the schema's slot names

## Extending Functionality

1. **Add a new entity type:**
   - Expose the class in `lib/api/api.yaml` and run `just gen-ui-config`
   - Add the key to `ENDPOINT_GROUPS` in `constants.ts` and to `API_ENDPOINTS` in `vite.config.ts`

2. **Customize UI:**
   - Modify layout dimensions in `constants.ts`
   - Edit component files in `components/ui/`
   - Adjust global styles in `app.css`
   - Adjust component styles in their colocated CSS files

3. **Add filters:**
   - Update `DROPDOWN_FIELDS` in `filters.svelte.ts`
   - Enable UI visibility via `UI_WANTED_FILTERS` in `constants.ts`

## Testing

- `npm run test` runs both Vitest projects. The **unit** project runs in node
  against `src/**/*.{test,spec}.{js,ts}` — state-class unit tests live in
  `src/lib/states/*.spec.ts` (asides, endpoint, filters, notify). The record
  form's helpers are tested in `src/lib/utils/recordForm.spec.ts`, and
  `src/lib/components/ui/Record/RecordForm.spec.ts` renders the form on the
  server, in node, from the real JSON Schema.
- The **browser** project (Vitest + Playwright + `vitest-browser-svelte`) runs
  files matching `*.svelte.spec.{js,ts}` under `src/` or `tests/`. Example
  components live in `tests/examples/`, and
  `src/lib/components/ui/Record/RecordForm.svelte.spec.ts` fills in and saves
  the record form in Chromium.
- Run one project with `npx vitest run --project unit` (or `browser`). The
  browser project requires Playwright's Chromium binary; install it once with
  `npx playwright install chromium`.

## Technology Stack

- **Svelte 5** with runes (`$state`, `$derived`, `$effect`, `$props`)
- **Vite 8** (Rolldown) + `@sveltejs/vite-plugin-svelte`
- **svelte-routing** for client-side routes
- **TypeScript 6**
- **Tailwind CSS 4** + **DaisyUI 5**
- **svelte-select** for dropdowns
- **@sjsf** (svelte-jsonschema-form) with its daisyUI 5 theme and **ajv** for the record form
- **Vitest 4** + **vitest-browser-svelte** + **Playwright** for tests
